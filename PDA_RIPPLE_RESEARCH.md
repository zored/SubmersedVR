# PDA glass touch ripples — feasibility

## Finding

Feasible as an extension of the existing screen-only refraction shader. It can show an expanding damped ring on press and a smoothly moving, gradually fading disturbance while the finger remains in contact. This is a visual approximation, not a fluid simulation, and does not need new physics colliders or a compute shader. The current `PDARefraction.shader` already calculates a screen-space sample offset from the surface normal and smooth UV waves, then takes five background samples; add a small bounded ripple contribution to that same offset rather than adding another GrabPass or extra texture samples. Give it a short attack and smooth decay to avoid flicker. Optional subtle rim lighting can make the effect visible on a low-detail background.

## Existing touch and coordinate constraints

- `PdaFingerPointer.Sync` records the animated index tip in UI space by subtracting `SNCameraRoot.main.transform.position`; `PdaTouchProbe` uses a UI-camera GraphicRaycaster and returns a UI `RaycastResult`. It is not a physics hit on the tablet mesh, and its position/UV must not be treated as the mesh UV. `PdaFingerTouch` knows valid contact, the initial `TouchEvent.Press`, ongoing `touch.Held` and release. Reuse these states without changing UI input.
- The model is under `Player.main.GetPDA().transform.Find("Mesh")`, and `PdaRefraction` replaces only the `PDA_screen` material slot. UI and the physical mesh have separate transforms and independently persisted scale and offset settings. Therefore establish the mapping empirically: UI touch point -> normalized screen-plane coordinates -> actual model screen plane (or convert the actual finger world position with the root translation and `renderer.transform.InverseTransformPoint`, after verifying physical and visual alignment). The shader can compare two positions in mesh-local screen-plane coordinates; calibrate axis order/sign/orientation and scale against screen corners and tilted/scaled PDA, not arbitrary whole-mesh bounds. This avoids relying on the mesh's texture UV layout. [Unity InverseTransformPoint](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/Transform.InverseTransformPoint.html).
- A physics `RaycastHit.textureCoord` only makes sense for a real MeshCollider hit; current `GraphicRaycaster` result does not supply it. Adding a collider just for this effect could affect gameplay and is unnecessary. [Unity textureCoord](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/RaycastHit-textureCoord.html).

## Suggested prototype

1. Press: record a local surface center, monotonic/unscaled start time and strength; create a short expanding ring. Evaluate e.g. `r = distance(surfacePoint, center)`, ring envelope `exp(-k * (r - speed * age)^2)` times a smooth age fade, with modest displacement amplitude. Cap extent to the screen surface; avoid changing panel content or input hit tests.
2. Hold and slide: interpolate a gently moving local distortion under the finger, optionally emit a bounded set of 4–8 weak, fading ring centers only after a minimum local travel distance or interval. Smooth coordinates and amplitudes; no frame-dependent spawn rate, no allocations each frame, no oscillating or accumulating waves when stationary. Clear on close, loss of contact, or unload; let emitted rings fade naturally if appropriate.
3. Pass local positions, times, active weights and an unscaled clock to the existing per-PDA `glass` material with `Material.SetVector`/`SetFloat` (it already owns an individual material instance). A reusable `MaterialPropertyBlock` and `Renderer.SetPropertyBlock(block, screenIndex)` is an alternative, but preserve existing overrides and restore them on close; the indexed block takes precedence over the renderer block. [Material.SetVector](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/Material.SetVector.html), [Renderer.SetPropertyBlock](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/Renderer.SetPropertyBlock.html), [Renderer.GetPropertyBlock](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/Renderer.GetPropertyBlock.html).
4. Continue using the existing stereo macros and shared object-local wave centers for both eyes. Test left/right alignment and sampling near eye viewport boundaries in the actual active stereo mode: successful bundle load and `shader.isSupported` do not establish correct stereo. [Unity 2019.4 single-pass instancing](https://docs.unity3d.com/2019.4/Documentation/Manual/SinglePassInstancing.html), [single-pass stereo](https://docs.unity3d.com/2019.4/Documentation/Manual/SinglePassStereoRendering.html).
5. Measure GPU/frame time in real VR before and after. Current shader already uses a `GrabPass` and five samples, and VR renders two views; bounded procedural arithmetic is expected to avoid additional screen grabs/samples but real cost depends on GPU, screen coverage and stereo mode. [Unity GrabPass](https://docs.unity3d.com/2019.4/Documentation/Manual/SL-GrabPass.html). This is a performance hypothesis, not a measurement.

## Important visual limitation

Current `GrabPass` bends pixels already rendered behind the glass. The PDA interface is rendered using a separate UI camera/layer, so it may be composited after the physical glass and remain sharp/unwarped; confirm actual draw order. A wave across the glass/background is supported by this design. If the user expects *text and icons* themselves to distort, a separate UI-layer effect/compositing path would be needed and must be evaluated independently for legibility, input and stereo.

## Validation not yet performed

No implementation or VR observation was performed in this research. Test mapping at four corners and center while the PDA moves/rotates/scales, click/hold/drag/release and rapid direction changes, both eyes, readability, visibility on plain backgrounds, no stale waves on reopen, and GPU frame time. The prior shader compatibility test only proved bundle load and platform support, not the new effect.
